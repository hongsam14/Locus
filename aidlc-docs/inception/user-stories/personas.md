# Personas — Locus

3개 페르소나. P1·P2는 1차 사용자(기획자 측), P3는 2차 소비자(런타임).

---

## P1 — 내러티브 디자이너 (Narrative Designer)

- **역할**: 세계관의 로어·문화·인물·사건·관습 등 **지식 콘텐츠**를 설계.
- **목표**: 자신이 쓴 비정형 메모·설정 문서가 구조화된 지식 그래프로 변환되고, 지역별로 "누가 무엇을 아는가"가 일관되게 표현되길 원한다.
- **주요 관심**: 엔티티/관계 추출 품질, 지식의 지역 스코핑, 소문·왜곡 표현, 상식 Wiki 기반 고증의 그럴듯함, 보강 Q&A로 빈틈 메우기.
- **기술 수준**: 비개발자~준개발자. CLI보다 **웹 UI** 선호. JSON 직접 편집은 가능하나 비선호.
- **불만(Pain)**: 설정이 문서 곳곳에 흩어져 재활용 안 됨, NPC마다 수동 스크립트 작성이 고통.
- **성공 모습**: 메모+지도를 넣으면 검토할 만한 초안 그래프가 나오고, 몇 번의 Q&A로 완성도가 올라간다.

## P2 — 월드/레벨 디자이너 (World / Level Designer)

- **역할**: 지도·지형·지역 구조 설계. 토폴로지(연결·접근성·단절)의 정확성에 책임.
- **목표**: 지도 이미지나 구조화 맵(GeoJSON 등)에서 지역 노드·계층(대륙>지방>마을>구역)과 지형 제약이 정확히 반영된 연결 그래프가 생성되길 원한다.
- **주요 관심**: 지역 식별 정확도, 계층 구조, 지형(산맥·강·길)에 따른 **연결 강도 가중**, 상식 Wiki의 물류·접근성 prior.
- **기술 수준**: 준개발자. 구조화 포맷 입력에 익숙. 웹 UI에서 토폴로지 시각·편집 선호.
- **불만(Pain)**: 지형의 의미(이 산맥은 교류를 끊는다)가 데이터로 표현되지 않음.
- **성공 모습**: 지도를 넣으면 지형 제약이 가중치로 반영된 토폴로지가 나오고, UI에서 손쉽게 보정한다.

## P3 — NPC 런타임 시스템 (NPC Runtime Consumer)

- **역할**: 게임 런타임의 NPC 대사·행동 생성 모듈(예: LLM 기반). **2차 소비자**.
- **목표**: "지역 X에 거주하는 NPC가 아는 지식"을 안정적인 계약(JSON)으로 가져가 컨텍스트로 쓰고 싶다.
- **주요 관심**: 쿼리 API의 명확한 스키마, **공유 지식 vs 지역 고유 지식 구분**, confidence·소문(variant) 메타데이터, 응답 지연.
- **기술 수준**: 시스템(자동화 클라이언트). 사람 아님 → UI 불필요, 결정적·버전 안정적 API 필요.
- **불만(Pain)**: 지식 출처가 비정형이라 NPC가 모르는 걸 알거나, 아는 걸 모름.
- **성공 모습**: 지역 ID로 호출하면 그 지역 NPC가 알 만한 지식만 메타데이터와 함께 정확히 받는다.
