# V5 GM 쓰기 정확성 — NFR (light: 요구 + 설계)

**원하시는 것**: Purpose Restructure 주기에서 넘긴 일을 처리해 솔로 TRPG를 다듬는 것. 이번 주기는 새 TRPG·판타지 디자인으로 화면 다시 만들기, 결과가 틀리는 결함 고치기, 시한 있는 부채 정리다.
**지금 하는 것**: V5 NFR(가벼운 판). 겹친 쓰기를 오프라인에서 어떻게 재현하고 확인할지(NFR-10), 실제 PostgreSQL 잠금을 운영자가 어떻게 확인할지, 그 밖의 NFR이 V5에 어떻게 걸리는지 정한다.

근거:
- 요구사항 `inception/requirements/follow-up-requirements.md` NFR-1~10
- 유닛 `unit-of-work.md` V5의 NFR light 항목(겹침 재현 테스트 방식, PostgreSQL 실제 잠금 운영자 확인 절차)
- 승인된 FD(`functional-design/*`, 2026-10-08). 리뷰 01의 R-01~R-06은 Accepted risk이고 코드 계획으로 간다. 그 가운데 **R-02**(시험 저장소)는 이 문서 § 2가 정한다.

### 1.1 성능과 자원

- **짧은 쓰기 구간의 길이**: 작업 단위 하나(읽기 몇 번, 쓰기 몇 번, 줄 하나)다. 인메모리·SQLite에서 밀리초, PostgreSQL에서 수 밀리초~수십 밀리초다. 기다림 상한 5초(`gm_write_wait_s`)는 무엇이 멈췄을 때만 걸린다.
- **늘어나는 일**: GM 쓰기마다 구간 안에서 세션과 바꿀 행을 한 번 더 읽는다(읽기 1~3회). 턴의 경로는 바뀌지 않는다. 일괄 생성 다섯은 LLM을 함께 부르고, 저장 다섯이 차례로 돈다(합쳐서 수십 밀리초).
- **잠금 수**: 세션마다 `RLock` 하나와 수 셋(턴 슬롯, 닫는 중, 리스). 지우지 않는다. 세션 수만큼이고 프로세스가 끝나면 사라진다.
- **시작 복구**: `running` run 수만큼 작업 단위 하나씩이다. 정상 종료면 0개다.
- **워커 하나**: 짧은 쓰기는 프로세스 안 잠금이다. `uvicorn --workers 1`(compose, `docker-compose.yml:147-148`)을 바꾸지 않는다. operations.md(116행 부근)는 이미 턴 guard 때문에 워커 하나를 요구한다. 짧은 쓰기도 같은 전제라는 것을 그 문단에 덧붙인다.

## 2. 오프라인 겹침 재현 (NFR-10, FD 리뷰 R-02)

### 2.1 두 저장소

| 저장소 | 만드는 법 | 겹침이 드러나는 곳 |
|---|---|---|
| 인메모리 `InMemoryPlayRepository` | 그대로 | 작업 단위가 저장소 전체 `RLock`을 쥐므로, **작업 단위 밖**의 읽기에서만 겹친다 |
| SQL 어댑터 `PostgresPlayRepository` on **SQLite 파일** | `create_engine(f"sqlite:///{tmp_path}/play.db", connect_args={"check_same_thread": False, "timeout": 5})`, 스키마 생성 | 작업 단위마다 `engine.begin()`이다. SQLite(pysqlite의 기본 트랜잭션 처리)는 SELECT에서 잠그지 않고 첫 쓰기에서 잠그므로, **작업 단위 안**의 읽기도 겹친다. `FOR UPDATE`는 SQLite에서 무시된다 |

- `sqlite://`(메모리 DB)는 쓰지 않는다. 연결마다 다른 DB라 스레드 둘이 같은 데이터를 보지 못한다.
- 두 저장소 모두 `tests/play/test_repository_contract.py`의 매개변수 방식을 따른다(픽스처 하나가 둘을 낸다). 새 포트 `list_running_runs`도 이 계약 시험에 더한다.

### 2.2 끼워 넣기 문

- 시험용 감싸개 `InterleaveGate`가 저장소를 감싼다. 정해진 메서드(예: `list_region_distortions`) 호출이 **끝난 직후** 그 스레드를 멈추고, 다른 스레드가 같은 자리에 오기를 최대 0.5초 기다린다. 둘이 모이면 함께 풀리고, 시간이 지나면 혼자 풀린다.
- **작업 단위의 저장소도 감싼다.** `uow()`가 돌려주는 작업 단위의 `.distortions`·`.events`·`.rumors` 같은 속성(인메모리에서는 저장소 자신, SQL에서는 `_PgStores`)이 감싼 객체를 돌려줘야 "작업 단위 안의 읽기 직후"에 멈출 수 있다. 감싸개는 `uow()`도 감싸서 감싼 작업 단위를 돌려준다.
- 문은 첫 두 호출에만 건다(그 뒤 호출은 그냥 지난다). 시험이 끝나면 문을 끈다.
- 고친 코드: 둘째 요청은 짧은 쓰기 잠금에서 기다리느라 문에 오지 못한다. 첫째의 문은 시간 초과로 풀리고 결과는 차례로 한 것과 같다. 시험 하나가 0.5초 남짓 늘어난다.
- 고치기 전 코드: 두 요청이 모두 읽은 뒤 쓰므로 결함이 드러난다.

## 3. 실제 PostgreSQL 확인 (운영자, B&T 체크리스트)

오프라인 시험은 PostgreSQL의 행 잠금을 돌리지 못한다(인메모리·SQLite). 아래는 실제 스택(`docker compose --profile service up`, 워커 하나)에서 운영자가 한 번 돌리는 확인이다. U3 #10(왜곡도 설정과 해소의 `FOR UPDATE`)과 함께 B&T 운영자 확인 목록에 넣는다.

| # | 확인 | 하는 법 | 바른 결과 |
|---|---|---|---|
| P1 | 두 사건 동시 해소 | 데모 세션에서 한 지역에 사건 둘을 만들고 턴 몇 번. 두 해소를 `curl … &`로 동시에 | 둘 다 해소, 지역 왜곡도가 사건 전 값 |
| P2 | 해소와 왜곡도 설정 동시 | 같은 지역의 해소와 설정을 동시에 | 설정값이 남고 사건 기여는 0(U3 #10 규칙) |
| P3 | 씨앗 시작 둘 | 같은 씨앗 시작을 동시에 | 201 하나, 409 `seed_running` 하나 |
| P4 | 닫기 중 생성(키 있을 때) | 소문 생성 요청 직후 세션 닫기 | 닫기 200, 생성 409 `session_closed`, 소문 0 |
| P5 | 재시작 복구 | 선언 행동 직후(LLM 서술 중) `docker compose restart app` | 다시 뜬 뒤 그 run이 `failed`/`interrupted`, 플레이어 위치·청구 복원(0턴이면), `turn_run_failed` 줄 |
| P6 | 플레이어 409 | GM 생성 중(키 있을 때) 플레이어 [기다리기] | 409 `gm_busy`, 문장에 run id·세션 id 없음, 화면에 "GM이 작업 중이에요" |

- P1~P3는 키 없이 된다. P4·P6은 키가 있어야 GM 쓰기가 몇 초 걸려 겹칠 틈이 생긴다.
- 확인 스크립트를 저장소에 두지 않는다(운영자가 curl로 한다). `scripts/live_scenario.py`에 넣을지는 B&T에서 정한다.

## 4. guard 상태 기계 속성 시험 (NFR-6)

hypothesis `RuleBasedStateMachine` 하나로 `TurnGuard`의 규칙을 본다. 스레드 없이 호출 순서만 섞는다.

- **규칙(동작)**: 턴 시작·끝, 리스 들어가기·나오기, 닫기 들어가기·나오기, 세션 둘.
- **불변식**
  - 한 세션에 턴과 리스가 함께 있지 않다.
  - 닫는 중에는 턴이 시작되지 않는다(`SessionClosedError`).
  - 턴이 있으면 리스·닫기가 `TurnInProgressError`다.
  - 리스가 있으면 턴이 `GmBusyError`다.
  - `turn_running`·`gm_busy`가 위 상태와 늘 맞는다.
  - 세션 둘은 서로 영향이 없다.
- 짧은 쓰기 잠금의 기다림·시간 초과는 상태 기계에 넣지 않는다(스레드가 필요하다). TP-V5-13이 본다.
