### Question 1
GM 쓰기가 겹칠 때 **어떻게 줄 세우시겠습니까?** (설계 메모 12, FR-C1·C2)

**배경**
- 지금 GM 쓰기는 세션 리스를 **함께** 쥔다(`locus/play/turn/guard.py` `hold`). 턴과는 서로 배타이고, GM끼리는 공유한다. 일괄 소문 생성이 다섯 지역을 동시에 돌 수 있도록 그렇게 했다(U7 #2).
- 그래서 GM 쓰기 둘이 같은 행을 "읽고 → 절대값으로 쓰면" 한쪽 결과를 잃는다. #9(동시 해소), #12(씨앗 이중 시작), RE-P01(지지도가 취소를 되살림), RE-P06(승인 겹침), 피드백 몫 이중 기록이 모두 같은 뿌리다.
- 세션 닫기는 턴만 보고 GM 쓰기는 보지 않는다(RE-P02).
- 이 답이 V5 유닛의 구조와 오프라인 테스트 방식(NFR-10)을 정한다.

A) **세션별 "짧은 쓰기 잠금"을 더한다** — 리스는 지금처럼 함께 쥐어 턴과 배타를 유지한다.
  - LLM 호출은 잠금 밖에서 하고, 읽고-쓰는 구간만 세션 잠금 안에서 줄 선다. 수 밀리초 동안 기다리고, 짧은 타임아웃이 지나면 409를 준다.
  - 세션 닫기와 월드 교체의 닫기도 이 잠금을 쥐고, 진행 중인 GM 쓰기를 본다.
  - 잠금은 프로세스 안에 있다(`--workers 1` 전제). 인메모리·SQLite 테스트에서 겹침을 그대로 재현할 수 있다. CLI 프로세스의 쓰기는 보지 못하지만, CLI는 GM 쓰기를 하지 않는다.
B) **DB 행 잠금** — 짧은 쓰기 트랜잭션마다 세션 행(또는 지역 왜곡도 행)을 `FOR UPDATE`로 잡는다. 프로세스와 무관하게 정확하다. 대신 오프라인 테스트(SQLite·인메모리)는 이 잠금을 재현하지 못해, 정확성을 운영자 확인에만 기대게 된다. UoW 밖에서 두 번 쓰는 서비스 다섯 곳도 모두 UoW로 옮겨야 한다.
C) **GM 쓰기끼리도 배타로 한다** — 겹친 GM 쓰기는 바로 409다. 가장 단순하다. 다만 일괄 생성(5개 동시)이 깨져서 순차로 바꿔야 하고, 느려진다(U7 #2를 되돌림). LLM 생성 동안 다른 GM 조작도 모두 막힌다.
X) Other (please describe after [Answer]: tag below)

- **권장: A.** 결함 다섯과 닫기 경합을 한 장치로 닫습니다. 일괄 생성의 동시성은 유지됩니다. 오프라인에서 겹침을 재현해 테스트할 수 있습니다(NFR-10).
- **A와 B의 차이**: A는 앱 프로세스 안에서 줄을 세우고, B는 데이터베이스가 줄을 세웁니다. 이 프로젝트는 워커 하나로 돌아서 A로 충분합니다.

[Answer]: A — 세션별 짧은 쓰기 잠금 (대화창 답변, 2026-10-07)

### Question 2
GM 쓰기가 진행 중일 때 **플레이어에게 무엇을 보이시겠습니까?** (#5(a), FR-C5)

**배경**
- 플레이어 화면의 `turn_running`은 지금 "턴 실행" 또는 "GM 쓰기 리스"를 뜻한다. GM이 소문을 생성하는 몇 초 동안 플레이어가 행동하면, 내부값이 섞인 409("…(run gm)")를 받는다.
- 턴과 GM 쓰기가 서로 배타인 것은 정확성 때문이다. GM 쓰기 중에 턴이 시작되면 승격된 소문이 지워졌다(U4-2 #7). 그래서 배타는 유지하고, 보이는 방식만 고르는 것이 이 질문이다.
- 이 답이 `RegionView`의 칸과 플레이 화면의 버튼 상태(V4·V5)를 정한다.

A) **"턴 진행"과 "GM이 손보는 중"을 따로 보인다** — 서버는 턴(`turn_running`)과 GM 리스(`gm_busy`, 새 칸)를 구별해 준다. 화면은 둘 다 버튼을 잠그되 문장을 다르게 보이고, GM이 끝나면 짧게 자동으로 다시 읽는다. 409 문장에 내부값이 없다.
B) **지금처럼 하나로 본다** — `turn_running` 하나로 보이고, 문장만 사람 말로 바꾼다("잠시 뒤 다시 시도해 주세요"). 서버 칸은 바뀌지 않는다. 플레이어는 왜 기다리는지 모른다.
X) Other (please describe after [Answer]: tag below)

- **권장: A.** 솔로 플레이에서 GM 모드는 같은 사람의 다른 탭입니다. "GM이 손보는 중"이 보이면 기다리는 까닭을 압니다. 칸 하나를 더하는 가산 변경입니다.

[Answer]: A — 턴과 GM 작업을 따로 표시(`gm_busy`) (대화창 답변, 2026-10-07)

### Question 3
자료로 **다시 빌드할 때 NPC와 사건 씨앗을 어떻게** 하시겠습니까? (FR-C9, 리뷰 R-04)

**배경**
- 지금 빌드는 NPC와 씨앗을 만들지 않는다. 교체할 때는 옛 월드의 것을 지운다(RE-W18). 제작자가 에디터에서 더한 NPC와 손으로 쓴 씨앗은 백업 파일에만 남는다.
- README는 "NPC가 만들어집니다"라고 적고 있다.
- 이 답이 제작자가 다시 빌드한 뒤 무엇을 보는지와, V7 유닛의 크기를 정한다.

A) **옛 월드의 NPC·씨앗을 새 월드에 이어 붙인다** — LLM 비용이 없고 결과가 결정적이다. README는 "빌드는 지역·연결·지식을 만들고, NPC는 에디터에서 더한다"로 고친다.
  - 집 지역과 씨앗 지역을 이름과 단계로 새 월드에서 찾아 붙인다.
  - 못 찾은 것은 빌드 리포트에 경고로 보이고 뺀다(백업에는 남는다).
  - 빌드 자체는 NPC를 만들지 않는다.
B) **A에 더해, 빌드가 NPC가 없는 지역에 NPC 초안을 만든다** — 지역마다 LLM 1회다(지금의 `NpcDraftService`를 쓴다). README 문장과 맞고, 새 월드도 바로 대화할 수 있다. 빌드 비용과 시간이 늘고(지역 12개면 +12회), 생성된 NPC의 질은 제작자가 확인해야 한다.

- **권장: A.** 결함(손작업을 잃음)을 닫는 최소 동작이고, 빌드 비용 상한이 없는 문제(RE-W08)를 키우지 않습니다. NPC 생성은 에디터의 [NPC 제안]으로 이미 할 수 있습니다.
- **A와 B의 차이**: B는 빌드 결과에 새 NPC가 생깁니다. A는 이미 있던 것만 지킵니다.

### Question 4
홈의 **데모 카드 문구와 월드 이름**도 한국어로 보이게 하시겠습니까? (FR-L3, 리뷰 R-02)

### Question 5
새 프리미티브의 **접근성 동작(대화상자, 탭, 선택 상자)을 무엇으로** 만드시겠습니까? (FR-D4, FR-S6)

**배경**
- 지금 프리미티브는 모두 직접 만든 것이다. Modal에 Esc 닫기와 포커스 관리가 없고, 탭에 화살표 키가 없다.
- 이번 주기는 접근성 자동 검사(axe)와 브라우저 E2E를 두지 않기로 했다(Q7=B). 그래서 접근성 동작이 맞는지는 사람의 확인과 jsdom 단위 테스트에 기댄다.
- 이 답이 웹 의존성과 V2 유닛의 크기, 번들 크기(NFR-4: JS gzip 1.3배 이내)를 정한다.

A) **검증된 headless 라이브러리 위에 스타일을 입힌다**(Radix UI 계열, MIT) — 대화상자의 포커스 가두기·복귀·Esc, 탭의 키보드 이동, 선택 상자의 키보드·스크린리더 동작을 라이브러리가 맡는다. 모양은 전부 우리 토큰으로 입힌다. 의존성이 몇 개 늘고, JS가 대략 15~30 kB gzip 늘어난다(예산 안).
B) **브라우저 기본 요소를 스타일링한다**(`<dialog>`, `<select>`) — 의존성이 늘지 않고 접근성은 브라우저가 맡는다. 펼친 선택 목록은 TRPG 톤으로 꾸밀 수 없다(브라우저 기본 모양). jsdom이 `<dialog>.showModal`을 온전히 흉내 내지 못해 테스트가 번거롭다.
C) **지금처럼 직접 만든다** — 의존성이 없다. 포커스 가두기, 로빙 탭인덱스, 선택 상자 키보드 동작을 직접 구현하고 테스트해야 한다. 자동 검사가 없어 빠진 동작을 놓치기 쉽다.
X) Other (please describe after [Answer]: tag below)

- **권장: A.** 자동 접근성 게이트가 없는 이번 주기에는, 검증된 동작을 빌려 쓰는 것이 빠진 동작을 놓칠 위험을 가장 줄입니다. 모양은 전부 우리 토큰이라 TRPG 톤을 해치지 않습니다.

[Answer]: A — headless 라이브러리(Radix UI 계열) + 우리 토큰 스타일 (대화창 답변, 2026-10-07)

### Question 6
서버 오류를 화면 문장으로 바꿀 때 **무엇을 근거로** 하시겠습니까? (FR-D9)

**배경**
- 지금 오류 응답은 `{"detail": "<영어 문장>"}`이다. 화면은 `String(e)` 42곳에서 원문을 그대로 보인다.
- 몇 곳은 문자열을 찾아 종류를 가른다. 예를 들어 `conflictKind`는 본문에서 "session is closed"를 찾는다. 서버 문장이 바뀌면 조용히 깨진다.
- 이 답이 API 오류 계약(V2·V5)과 프론트 오류 문장 모듈을 정한다.

A) **서버가 기계가 읽는 `code` 칸을 더한다** — 예: `{"detail": "...", "code": "session_closed"}`. 가산 변경이라 `detail`은 그대로다. 프론트는 `code`로 문장을 고르고, 모르는 코드는 상태 코드별 일반 문장을 쓴다. 서버의 오류 종류마다 코드 하나를 둔다.
B) **서버는 그대로 두고, 프론트가 상태 코드와 지금 detail 문자열로 고른다** — 서버를 바꾸지 않는다. 문자열 매칭이 늘어나, 서버 문장을 바꿀 때마다 화면이 조용히 틀릴 위험이 커진다.
