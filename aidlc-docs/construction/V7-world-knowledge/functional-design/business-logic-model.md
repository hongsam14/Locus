# V7 월드·지식 정확성 — Business Logic Model

**원하시는 것**: Purpose Restructure 주기에서 넘긴 일을 처리해 솔로 TRPG를 다듬는 것. 이번 주기에는 세 가지를 한다.
- 새 TRPG·판타지 디자인으로 화면을 다시 만든다.
- 결과가 틀리는 결함을 고친다.
- 시한이 있는 부채를 정리한다.

**지금 하는 것**: V7 Functional Design. 이 문서는 V7이 바꾸는 흐름을 정한다.
- 합의 출처 고르기와 정렬
- 캐시와 저장 순서
- 백업 게이트
- 이어 붙이기
- 중복 id
- 라벨 있는 읽기·삭제
- 보강 입력 칸

값과 포트는 `domain-entities.md`, 규칙과 시험은 `business-rules.md`에 있다.

## 1. 합의 — "이 지역 NPC가 아는 것" (FR-C6, RE-W01, Q1 = A)

`compute_consensus(region_id, …)`는 단계 차례를 그대로 둔다. 바뀌는 곳은 4단계와 정렬이다.

0. **직접 스코프 모으기**: `region_direct[지역]`을 만들 때, 같은 (지역, 지식)의 직접 스코프가 둘 이상이면 확신이 가장 높은 하나만 둔다. 지금은 먼저 나온 것이 이겨 입력 순서에 따라 결과가 달라진다(설계 리뷰 01 R-07).
1. **직접**: 이 지역의 직접 스코프 지식
2. **이어받음**: 조상 지역의 직접 스코프 지식(가까운 조상부터, 이미 정해진 지식은 건너뜀)
3. **전역**: 전역 지식(이미 정해진 것은 건너뜀)
4. **전파와 전언**
   1. `pw = best_path_weights(region_id, connections)`. 바뀌지 않는다.
   2. `origins = best_origins(pw, region_direct, exclude=region_id)`: 지식마다 가장 강한 출처를 고른다. 동률이면 지역 id가 작은 쪽이다.
      - 가중은 정확히 비교한다. `best_path_weights`는 연결 순서와 무관하게 비트까지 같은 값을 낸다. 반올림해 비교하면 마지막 비트만 약한 출처가 "동률"로 이겨, 그 가중으로 묶음이 정해진다(코드 리뷰 01 #1).
   3. 지식 id 순으로 `origins`를 돈다. 이미 1~3단계에서 정해진 지식은 건너뛴다.
      - 출처 가중 `w`가 `propagate_min` 이상이면 **전파**다. 유효 확신도는 `k.confidence × w`다.
      - `hearsay_min` 이상이면 **전언**이다. 유효 확신도는 같고, `path_decay = 1 − w`다.
      - 그보다 약하면 `unknown_count += 1`이다. 지식마다 한 번만 센다.
5. **정렬**(Q1 = A): 다섯 목록 각각을 `confidence` 내림차순으로 정렬하고, 같으면 `knowledge_id` 오름차순이다. 묶음 사이 차례(직접 → 이어받음 → 전역 → 전파 → 전언)는 그대로다.

- **지금과 달라지는 것**
  - 출처를 사전(dict) 순회에서 처음 만난 지역으로 고르지 않는다. 가장 강한 경로의 지역을 고른다.
    - 그래서 0.9 경로로 닿는 지식이 0.3 경로 출처에 잠겨 전언이 되는 일이 없어진다.
    - 같은 월드를 몇 번 로드해도 같은 결과가 나온다.
  - `unknown_count`가 부풀지 않는다. 지금은 (출처, 지식) 쌍마다 세고, 다른 출처로 이미 정해진 지식도 센다.
  - 플레이 화면의 "아는 것"과 "전해 들은 것"이 확실한 것부터 나온다. 휴대폰의 첫 3개도 그렇다(V4).
- **이 결과를 쓰는 곳**(설계 리뷰 01 R-06)
  - `play/region_knowledge.py`(플레이 장면의 "아는 것"·"전해 들은 것", 세션 질의)와 GM 지식 접힘은 합의의 차례를 그대로 보인다.
  - 에디터 인스펙터는 합의를 거치지 않고 저장된 차례로 지식을 보인다. 합의 차례가 아니다(코드 리뷰 01 #20). 에디터 배치는 V8 몫이다.
  - NPC 대화 범위 `play/npc/scope.py` `pick_facts`는 자기 키(직접 → 이어받음 → 전역, 그다음 확신)로 다시 정렬한다. 같은 뜻의 키라 결과는 같다. 동률의 차례만 이제 지식 id로 고정된다. 바꾸지 않는다.
  - 소문 씨앗 `play/rumor/service.py`(`_collect_sources`)는 `direct + propagated`를 합의 차례로 읽는다. 그래서 이 지역의 직접 지식이 확실한 것부터 먼저 오고, 그다음 전파된 지식이 확실한 것부터 온다.
    - 0.3짜리 직접 지식이 0.9짜리 전파 지식보다 먼저 소문이 된다(코드 리뷰 01 #20). 상한이 있을 때는 각 묶음 안에서 더 확실한 지식이 먼저다.
    - 씨앗 차례를 단언한 시험이 있으면 고친다.

## 2. 캐시와 저장 순서 (FR-C7, RE-W02, RE-W03, R-08)

### 2.1 `persist_graph`

```
노드(WorldMeta 제외) upsert → 엣지 upsert ─┬─ 실패: error 경고, 돌아감 (WorldMeta 안 씀)
                                         └─ 성공 → 임베딩 → 색인(실패: error 경고, 계속) → WorldMeta upsert(실패: error 경고)
```

- WorldMeta는 그래프가 다 써진 뒤에만 써진다. 그래서 버전 표식이 연결·스코프보다 먼저 새 값이 되지 않는다.
- 노드·엣지 실패나 색인 실패는 지금처럼 error 경고다. 리포트는 `ok=false`다.
  - 노드·엣지가 실패한 월드에는 WorldMeta가 없다. 그 월드는 §2.2에 따라 캐시되지 않는다.
- 빌드는 지금 `persist_graph`를 여러 번 부른다(사전 → 온톨로지 사전 → 본체). WorldMeta는 **본체 호출에만** 실린다. 이어 붙인 NPC·씨앗도 그 본체 호출에 함께 싣는다(§4).
- World File 불러오기는 한 번 부른다. 메타도 그 한 번에 마지막으로 쓴다.
- 에디터의 `touch_world_meta`는 그대로다. 편집이 끝난 뒤 버전을 올린다.

### 2.2 `WorldCache.get`

1. **hit**
   - 버전 확인을 켜 둔 캐시면 지금 버전 표식을 읽는다.
     - 읽기가 예외를 내면 항목을 버린다(invalidate). 그리고 4로 간다. 다음 읽기가 버전을 다시 보도록 캐시하지 않는다(RE-W03).
     - 캐시한 버전과 같으면 hit를 돌려준다. 다르면 항목을 버리고 miss로 간다(지금과 같음).
   - 캐시한 버전이 `None`인 항목은 이제 생기지 않는다(3).
2. **miss**: 불러오기 **전에** 버전 표식을 읽는다(지금과 같음). 읽기가 예외면 캐시하지 않는다.
3. **버전이 `None`이면**(WorldMeta 없음) 캐시하지 않는다. 바뀐 점이다. 지금은 `None`으로 캐시해 그 뒤로 버전 확인을 건너뛰었다.
   - 이 규칙은 **버전을 읽을 수 있는 캐시**(버전 확인이 켜져 있고 로더에 `version()`이 있음)에만 걸린다. 그 로더가 이 월드에 대해 `None`을 돌려줄 때다(설계 리뷰 01 R-01).
   - 로더에 `version()`이 없거나 `check_version=False`인 캐시는 지금처럼 캐시하고, 명시적 무효화만 따른다. 기존 `tests/knowledge/test_cache.py`의 EX-18·EX-19(버전 없는 대역 로더)는 그대로 통과한다.
   - 구별 방법: `_current_version`의 "로더에 버전이 없음"과 "이 월드의 버전이 없음"을 다른 값으로 돌려준다. 예: 로더에 `version`이 없으면 표식 상수 `UNVERSIONED`.
4. 불러온 스냅샷을 돌려준다. 캐시는 2·3의 조건과 "그 사이 invalidate가 없었음"(generation)을 모두 채울 때만 한다.

- **다른 프로세스(CLI)가 교체하는 동안 API가 읽으면**
  - 옛 월드가 지워진 틈: 버전 `None`(메타가 지워짐)이다. 반쪽 스냅샷을 그 읽기에만 쓰고 캐시하지 않는다.
  - 새 노드·엣지가 쓰이는 중: 아직 메타가 없어 `None`이다. 같다.
  - 메타까지 쓰인 뒤: 새 버전이다. 다 쓰인 스냅샷을 불러와 캐시한다.
  - 그래서 연결 0·스코프 0인 스냅샷이 새 버전 표식으로 캐시되는 일(RE-W02)이 없다.
- **비용**: WorldMeta가 없는 옛 월드(U2 이전에 만든 것)는 읽을 때마다 Neo4j에서 불러온다. 다시 빌드하거나 World File로 다시 불러오면 메타가 생긴다. 운영 문서에 한 줄 적는다.

## 3. 백업 게이트 (FR-C8, RE-W04, R-02)

빌드와 불러오기 모두 커밋 단계 맨 앞에서 이렇게 한다.

```
exists?
 ├─ 아니오 → (백업 없음) 저장
 └─ 예 → 옛 스냅샷 읽기(빌드만, §4; 실패 → 멈춤, 아래와 같음) → _backup
          ├─ 미설정 → None, 계속(테스트 빌더. API와 CLI는 백업을 설정한다, 코드 리뷰 01 #20)
          ├─ 성공 → 경로, 계속 → delete_world → 저장 …
          └─ BackupFailedError → 멈춤: 아무것도 지우지 않음
                                  리포트: replaced=false, backup_path=None,
                                          경고 stage "backup", severity error → ok=false
```

- 백업은 지우기 **전에** 끝나야 한다. 실패하면 옛 월드는 손대지 않은 채 남는다.
- 지금은 백업 실패가 일반 경고로 삼켜지고 교체가 진행되어 `ok=true`다. 그래서 편집한 월드를 되살릴 길 없이 잃을 수 있었다.
- 열린 세션 닫기는 API·CLI 층이 빌드·불러오기 **뒤에**, 리포트가 `replaced=true`일 때만 한다(`api/routers/world.py` `_close_if_replaced`, CLI도 같음). 이 순서는 바뀌지 않는다.
  - 그래서 백업 실패나 옛 월드 읽기 실패로 멈추면(`replaced=false`) 세션은 닫히지 않고 그대로 열려 있다(설계 리뷰 01 R-04).

## 4. 이어 붙이기 — 다시 빌드해도 NPC·씨앗이 남는다 (FR-C9, RE-W18, Q3=A)

빌드의 커밋 단계 순서(교체일 때):

1. **옛 스냅샷 읽기**: 캐시를 거치지 않은 새 읽기여야 한다(R-02). 빌더는 로더를 따로 갖지 않는다. 그래서 이미 가진 캐시로 `self._cache.invalidate(world_id)` 다음 `self._cache.get(world_id)`를 한다. 무효화 뒤의 `get`은 캐시의 로더로 새로 불러온다(설계 리뷰 01 R-08).
   - 이 방법이면 빌더의 생성자와 생성 자리 다섯 곳(`world/wiring.py`, CLI, 시험 빌더들)을 바꾸지 않는다.
   - 읽기가 `LookupError`(월드 없음)면, 준비하는 사이 다른 프로세스가 월드를 지운 것이다. 새 빌드로 다룬다: 이어 붙일 것도, 백업·지우기도 없다(코드 리뷰 01 #13).
   - 그 밖의 이유로 읽기가 실패하면 백업 실패와 같이 **교체하지 않는다**.
   - 경고 `stage="carry-over"`, severity error와 `"the old world could not be read; it was not replaced: …"`를 남긴다. 리포트는 `replaced=false`, `ok=false`다.
   - 까닭: 읽지 못하면 이어 붙일 수 없고, 백업이 미설정이면 NPC·씨앗이 어디에도 남지 않는다(FR-C9의 "잃지 않는다").
2. **백업**(§3)
3. `delete_world` → 캐시·검색 정리(지금과 같음)
4. 사전 저장, 온톨로지(지금과 같음)
5. `carry = carry_over(old, topology.regions, world_id)`
6. **본체 저장**: 새 월드 + `carry.npcs` + `carry.seeds`를 한 `persist_graph`로 쓴다. WorldMeta는 마지막이다.
7. 리포트에 `carried_npcs`, `carried_seeds`를 적고 `carry.warnings`를 더한다(못 붙인 것마다 하나). 본체 쓰기가 노드·엣지에서 실패하면 붙인 수는 0이다(코드 리뷰 01 #10).

- **로더가 이미 버린 NPC·씨앗**(집 지역이 없거나 노드를 읽을 수 없음)도 하나마다 경고한다. 이것들은 백업에도 없다. 백업이 같은 로더로 내보내기 때문이다(코드 리뷰 01 #2).

- **맞추기 규칙**(domain-entities § 4)
  - 옛 지역의 (정규화한 이름, 단계)로 맞춘다.
  - 같은 열쇠의 새 지역이 여럿이거나, 옛 월드에 같은 열쇠의 지역이 여럿이면 부모의 열쇠도 맞아야 한다(코드 리뷰 01 #11: 옛 Mill/North의 사람이 새 Mill/South로 가지 않는다).
  - 그래도 하나가 아니면 붙이지 않고 경고를 남긴다.
- **id는 그대로 둔다**
  - 같은 월드를 다시 빌드하므로 NPC·씨앗 id가 다른 노드와 부딪히지 않는다(옛 것은 지워졌다).
  - 교체 뒤 번역 정리(V3, `purge_world_translations`)는 새 월드에 있는 id의 번역을 남긴다. 그래서 이어 붙인 NPC·씨앗의 번역이 그대로 쓰인다(원문이 같아 해시도 같다).
- **NPC의 다른 참조**: NPC 모델은 집 지역 하나만 가리킨다(`home_region_id`). 씨앗은 지역 하나(`region_id`)다. 다른 참조는 없다.
- **세션**: 교체가 끝나 `replaced=true`가 되면 API·CLI 층이 열린 세션을 닫는다(V5·U8 규칙, § 3). 옛 세션의 NPC 대화 기록은 닫힌 세션에 남는다.
- **불러오기(World File)는 이어 붙이지 않는다**. 파일이 월드 전체를 담고, 파일에 NPC·씨앗이 있다.
- **README**: "NPC가 만들어집니다"를 고친다 — "빌드는 지역·연결·지식을 만듭니다. NPC와 사건 씨앗은 에디터에서 더하고, 소스로 다시 빌드해도 남습니다(지역 이름이 바뀌면 경고로 알립니다)."

## 5. 중복 id (FR-C10, U8 #10)

World File 불러오기:

0. 존재 검사(`replace=False`면 409) — 중복 검사보다 먼저다(코드 리뷰 01 #12)
1. **`duplicate_ids(file)`** — 새 단계다. **재매핑 전의 파일**에서 센다. 그래야 문장이 설계자가 고칠 파일의 id를 말한다(코드 리뷰 01 #12). 재매핑은 id마다 하나라 결과는 같다. 비어 있지 않으면 멈춘다.
2. 재매핑(`remap_ids` 또는 `set_world_id`) — 지금과 같다
   - 리포트: `replaced=false`, 경고 `stage="duplicate-ids"`, severity error, message `"duplicate ids in the World File: a, b, …"`(최대 10개와 "외 N개")
   - 아무것도 지우거나 쓰지 않는다. 옛 월드가 그대로 남는다.
3. `validate_references` → 겹친 스코프 모으기(같은 (지식, 지역)은 가장 높은 확신 하나, 코드 리뷰 01 #19) → 백업(§3) → 교체(지금과 같음)
   - 빌드의 `remap_scopes`(의미 중복 합치기 뒤)도 같은 쌍은 가장 높은 확신을 둔다. 그래프는 쌍마다 SCOPED_TO 엣지 하나라 저장 전에 모아야 BR-V7-02가 저장된 월드에서도 선다.

- 재매핑은 id마다 같은 공식(`uuid5(target:old)`)이다. 그래서 파일 안의 중복은 재매핑 뒤에도 중복이다. 검사를 재매핑 뒤에 해도 같은 결과다. 실제로 쓰일 id를 보는 것이 목적이다.
- 데모 불러오기(`world demo`)도 이 불러오기를 거치므로 같은 검사를 받는다. 데모 검사(`check`)는 V3 것을 그대로 쓴다.

## 6. 라벨 있는 읽기·삭제 (FR-C10, R-05)

호출부는 production에 **12곳**이다(설계 리뷰 01 R-05가 셈을 바로잡음; 상위 설계 리뷰의 11은 `delete_held`의 읽기와 삭제를 한 곳으로 셌다). 9곳은 라벨을 넘기고, 3곳은 라벨 없이 남는다. `apply.py`의 더한 노드 삭제에는 스냅숏이 없는 id의 라벨 없는 갈래가 하나 더 있다.

| 호출부 | 지금 | 바뀜 |
|---|---|---|
| `editor/writes.py` `node(world, id, label)` | 라벨 없이 읽고 라벨 비교 | `get_node(…, label=label)` |
| `editor/writes.py` `own_label` | 라벨 없이 읽어 다른 라벨이면 400 | 자기 라벨로 먼저 읽는다. 없을 때만 라벨 없이 읽어 다른 라벨이면 400. 옛 중복(V7 전)의 항목도 편집된다(코드 리뷰 01 #4) |
| `editor/writes.py` `delete_held` 읽기·삭제 | 라벨 없이 읽어 다른 라벨이면 손대지 않음 | 먼저 `get_node(…, label=label)`. 있으면 `delete_node(…, label=label)`와 그 문서 지우기. 없으면 라벨 없이 한 번 더 읽는다. 그 id의 노드가 아예 없으면 문서만 지운다(끊긴 삭제의 뒷정리, 지금 규칙). 다른 라벨 노드가 있으면 아무것도 지우지 않고 False다. 그 노드의 검색 문서도 그대로다(설계 리뷰 01 R-02) |
| `editor/regions.py` 씨앗·NPC·지역 삭제 | 라벨 없이 | `EventSeed` / `NPC` / `Region` |
| `editor/bundle.py` `delete_any` | 라벨 없이 읽어 라벨로 갈래 | 질문의 대상 종류(`knowledge`·`entity`)로 그 편집기의 라벨 있는 삭제를 부른다. 읽지 않는다(코드 리뷰 01 #4) |
| `augmentation/apply.py` 다시 가리키기 | 라벨 없이 읽어 기대 라벨과 비교 | `label=기대 라벨`로 읽는다 |
| `augmentation/apply.py` 되돌리기 검사 | 라벨 없이 | `label=snap.label` |
| `augmentation/apply.py` 더한 노드 삭제 | 라벨 없이 | `nodes_after` 스냅숏의 라벨로 지운다. 스냅숏이 없는 id는 라벨 없이 지운다(지금과 같음) |
| `augmentation/apply.py` `_nodes` 스냅숏 | 라벨 없이 | 대상 종류의 라벨로, 더한 노드는 `Knowledge`로 찍는다. 옛 중복에서 다른 종류를 찍어 되돌리기가 반만 되돌리지 않는다(코드 리뷰 01 #4) |

- 코드 리뷰 01 뒤 라벨 없이 남는 읽기는 둘이다. `own_label`과 `delete_held`의 두 번째 읽기("이 id를 다른 종류가 쥐었는가")다. 더한 노드 삭제의 스냅숏 없는 갈래도 남는다.
- 사전 저장(`WikiAdmin.upsert_prior`)도 `own_label`로 다른 종류의 id를 막는다(코드 리뷰 01 #17).
- 에디터 쓰기 뒤의 WorldMeta 갱신(`touch_world_meta`)은 있는 노드만 고치는 포트 `update_node`를 쓴다. 읽고 쓰는 사이에 다른 프로세스가 월드를 지워도 반쪽 월드에 표식을 되살리지 않는다(코드 리뷰 01 #14).
- 라벨이 주어지면 Neo4j 질의가 그 라벨에만 걸린다. 그래서 같은 id를 다른 라벨이 써도 그 노드는 읽거나 지우지 않는다(`DETACH DELETE`로 연결까지 지우던 U8 #10).
- 라벨 없는 세 곳은 이렇게 다룬다.
  - 중복 id를 불러오기에서 막는다(§5).
  - 에디터는 `own_label`로 같은 id의 다른 라벨 생성을 막는다(지금 규칙).
  - 그래서 새로 생기지 않는다. 이미 저장된 옛 중복은 지금처럼 남는다.

## 7. 보강 질문의 입력 칸 (FR-C12, U8 #13)

1. 질문을 만들 때 `NEEDS[(issue.type, issue.target_kind)]`로 입력 칸을 정한다(domain-entities § 8). 엔티티 대상의 고치기에는 제목 칸이 없다.
2. 답을 적용할 때(`apply._write`) 바꿀 값이 없으면 `ValueError`(400 `invalid_request`)다. 이 검사는 **쓰기 전에** 한다. 바꿀 칸을 먼저 계산하고, 비면 아무것도 쓰지 않고 변경 기록도 만들지 않은 채 던진다.
   - 고치기 / 더하기 / 다시 가리키기에서 바꿀 값이 없다는 것은 두 경우다.
     - 그 행동이 받는 칸이 모두 비었다.
     - 값이 지금 값과 모두 같다.
   - 변경 기록(change set)을 만들지 않는다. 질문은 열린 채다.
   - 문장: `"the answer changes nothing"`. 화면 문장은 `describeError`의 `invalid_request`다.
3. 확인(CONFIRM)은 "이대로 둔다"는 결정이라 거절하지 않는다(설계 리뷰 01 R-03).
   - 확신이 이미 목표값이어도 받는다. WIKI_CONFLICT는 확신과 무관하게 탐지되므로, 확인을 막으면 [두기] 말고 길이 없어진다.
   - 값을 바꾸지 않는 확인은 아무것도 쓰지 않고 변경 기록도 없다(FD 리뷰 02 R-09).
   - WIKI_CONFLICT의 확인과 값을 바꾸지 않는 확인은 run의 `kept_keys`에 들어가 그 run에서 다시 묻지 않는다(세션 확인 S-1). 그 확인을 되돌리면 열쇠가 빠지고 다시 묻는다(코드 리뷰 01 #3).
4. 비교는 저장될 꼴로 한다: 문장·제목은 다듬고, 공백뿐인 칸은 없는 칸이다(코드 리뷰 01 #15).
5. 자리 정하기·범위·다시 가리키기 답도 지금 값과 같으면(인스펙터에서 이미 고친 뒤의 낡은 질문) 쓰기 전에 거절한다(코드 리뷰 01 #16).

- 지금은 엔티티 질문에 제목 칸이 생긴다. 제목만 보내면 엔티티에는 제목이 없어 아무것도 바뀌지 않는데, 변경이 기록되고 같은 질문이 다시 나온다.
