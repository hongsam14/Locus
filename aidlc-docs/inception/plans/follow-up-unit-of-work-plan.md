### UOW-Q1
유닛을 **몇 개로** 나누시겠습니까?

**배경**
- 실행 계획의 초안은 아홉 개다. V1 CI → V2 디자인 시스템 → V3 한국어 백엔드 → V4 홈·플레이 → V5 GM 정확성 → V6 GM 화면 → V7 월드 정확성 → V8 에디터(P1) → V9 부채·문서.
- 유닛마다 승인 지점이 있다: FD, (NFR), 코드 계획, 코드. 유닛이 많으면 승인 횟수가 늘고, 적으면 한 번에 검토할 양이 커진다.
- 이 답이 Construction 단계의 승인 횟수와 유닛당 리뷰 크기를 정한다.

A) **아홉 개 그대로** — 유닛마다 초점이 하나라 리뷰가 적당한 크기다. 시간이 모자라면 V8(에디터)만 떼어 넘길 수 있다. 승인 지점은 대략 30번이다.
B) **일곱 개로 합친다** — V3+V4(한국어 백엔드 + 홈·플레이), V5+V6(GM 백엔드 + GM 화면)을 묶는다. 승인 지점이 줄고, 백엔드와 그것을 쓰는 화면을 한 번에 본다. 대신 유닛 하나에 백엔드·프론트가 섞여 코드 리뷰가 커지고, 중간에 멈추기 어렵다.
C) **다섯 개로 크게 묶는다** — CI, 디자인 시스템, 백엔드 정확성 전부(V3·V5·V7), 화면 전부(V4·V6·V8), 부채·문서로 나눈다. 승인 지점이 가장 적다. 화면 유닛 하나가 네 화면을 모두 다뤄 매우 크고, 에디터만 떼어 넘기기 어렵다.
X) Other (please describe after [Answer]: tag below)

- **권장: A.** 지난 주기(8유닛)와 같은 크기로, 리뷰와 되돌리기가 쉽습니다. 에디터(P1)를 넘길 자리도 남습니다.

[Answer]: A — 아홉 개 그대로 (대화창 답변, 2026-10-07)

### UOW-Q2
**mypy CI 게이트를 어느 유닛에 둘까요?** (설계 리뷰 R-09)

**배경**
- mypy 오류는 지금 11건이다. 그래서 게이트를 켜기 전에 0으로 만들어야 한다.
- V1은 2026-10-19 시한이 있는 CI 액션 정리다.
- 이 답이 V1의 크기와 시한 위험을 정한다.

A) **V9에서** — 11건을 고치고 CI에 mypy를 켠다. V1은 액션 버전과 러너만 맡아 가장 작게 끝난다. 그 사이 유닛들의 mypy는 사람(나)이 로컬에서 돌리고, 기준선이 늘지 않게 지킨다.
B) **V1에서** — 11건을 고치고 게이트까지 켠다. 이후 모든 유닛의 PR이 mypy 게이트를 받는다. 대신 V1이 커지고, 11건 가운데 langchain 타입(4건)이 까다로우면 시한에 걸릴 수 있다.
X) Other (please describe after [Answer]: tag below)

- **권장: A.** 시한이 있는 유닛은 작게 두는 것이 안전합니다. 기준선은 유닛마다 로컬에서 확인합니다.

[Answer]: A — V9에서 (대화창 답변, 2026-10-07)

### UOW-Q3
**V1(CI 시한)을 어떻게 내보내시겠습니까?**

**배경**
- PR #4를 병합한 뒤 이번 주기는 `feat/follow-up` 브랜치에서 한다(Workflow Planning 결정).
- 주기 전체는 4~6일이 걸리고, 사람이 기다리게 하는 지점이 있다. 그래서 주기 끝의 PR이 10-19 전에 병합된다는 보장이 없다.
- 2026-10-19가 지나면 `ubuntu-latest`가 Ubuntu 26으로 바뀐다. 액션이 맞지 않으면 main의 CI가 깨진다.
- 이 답이 브랜치·PR 구성을 정한다. 푸시와 병합은 사람의 일이다.

A) **V1만 main에서 짧은 브랜치(`chore/ci-actions`)를 따로 내서 작은 PR로 먼저 올린다** — 주기 길이와 상관없이 시한 전에 main이 안전해진다. `feat/follow-up`은 그 PR이 병합된 뒤 main을 받아 들인다(merge). 브랜치와 PR이 하나씩 는다.
B) **`feat/follow-up`에 넣고 주기 끝에 한 번에 PR로 올린다** — 브랜치가 하나라 단순하다. 주기 PR이 10-19 뒤에 병합되면 그 사이 main의 CI가 깨질 수 있다.
X) Other (please describe after [Answer]: tag below)

- **권장: A.** 시한이 주기 일정에 묶이지 않습니다. 작은 PR이라 리뷰와 병합이 빠릅니다.

[Answer]: A — V1만 main에서 `chore/ci-actions`로 따로 작은 PR (대화창 답변, 2026-10-07)

### UOW-Q4
화면 유닛(V2·V4·V6·V8)이 끝날 때마다 **결과를 어떻게 보시겠습니까?**

**배경**
- 레이아웃 자동 게이트가 없다(Q7=B). 화면은 사람이 확인하고, 최종 확인은 Build and Test에서 한다.
- 실행 계획은 화면 유닛마다 "빠른 확인"을 두었다. 문제를 일찍 보면 뒤 유닛이 같은 실수를 덜 한다.
- 실제 스택을 띄우려면 compose나 호스트 개발 서버가 필요하다. 이 호스트는 3000 포트가 다른 서비스에 잡혀 있어 `WEB_PORT=13000`을 썼다.
- 역공학 때는 가짜 API와 headless Chrome으로 1280·390px 캡처를 만들었다(실제 프론트 빌드).

A) **유닛마다 제가 가짜 API로 1280·390px 캡처를 만들어 비공개 Artifact 페이지로 보여 드린다. 실제 스택 확인은 Build and Test에서 한 번 한다** — 띄우는 수고 없이 매 유닛 결과를 본다. 캡처는 가짜 데이터라 실제 LLM 응답·번역 warm은 보이지 않는다. 캡처 도구는 저장소 밖(세션 스크래치)에 둔다.
B) **유닛마다 사람이 실제 스택(dev 서버나 compose)에서 직접 본다** — 가장 정확하다. 매번 띄우고 데모를 준비하는 수고가 든다. compose는 띄우기 전에 여쭙는다.
C) **중간 확인 없이 Build and Test에서 한 번에 본다** — 수고가 가장 적다. 문제를 늦게 알아 여러 화면을 함께 고치게 될 수 있다.
X) Other (please describe after [Answer]: tag below)

- **권장: A.** 매 유닛 결과를 빠르게 보면서 기다리는 시간을 줄입니다. 실제 동작은 마지막에 실제 스택으로 한 번 확인합니다.
- **A와 B의 차이**: A는 제가 만든 캡처를 보시는 것이고, B는 직접 앱을 조작해 보시는 것입니다.

[Answer]: A — 유닛마다 가짜 API 캡처(1280·390px)를 비공개 Artifact로, 실제 스택은 B&T에서 (대화창 답변, 2026-10-07)
